# SPA-055: Fable fills the cares gaps that Scryfall's tags leave

**Goal.** The owner said on 2026-11-05: "Fable needs to fill in the gaps where the Scryfall tags haven't been applied." After SPA-054, a card cares about a fact only when Scryfall gave it a "matters" or "synergy" tag listed in `cares.json`. This ticket adds a Fable pass that reads every card, its facts and its Scryfall-derived cares, then adds `cares:` tags only where none cover the idea, each with a reason.

The vocabulary goes in the packet, so Fable uses Scryfall's names rather than inventing its own (Architect's answer to the owner, 2026-11-05). Fable may also suggest new `cares.json` entries; those go to the Architect and are never applied automatically. The Architect runs it on trk after merge.

## Background the Developer needs

- Read SPA-054 (otags files, `CaresTable`, `CaresTerm`, known fact names), SPA-047 and SPA-052 (packets, import check lists, blind checks) and SPA-050's independence test.
- **Packet.** `spa cares-packet <set> --out <dir> [--otags <file>]` writes:
  - `instructions.md`: the prompt, then the `cares.json` table as a readable list, then the format brief and theme counts as in the tags packets;
  - the grade packet's `cards-NN.json` files, byte-identical;
  - `facts.json`: each card's code facts plus its `otag:` facts;
  - `cares-NN.json` beside each card file: each card's current cares tags, from `cares.json`;
  - `vocabulary.json`: every fact name a cares tag may use, each with its description. That is every code fact present in the set, and every Scryfall tag present in the set plus their ancestors, with Scryfall's `description` where it has one. Name tags (`name-matters` and its descendants, `tutor-self`) are left out: the owner's Andromedan Automatons check must stay independent;
  - `cares-gaps.schema.json` and `cares-table-suggestions.schema.json`.

  The packet is byte-identical across runs, passes `BlindCheck`, and passes SPA-050's independence test.
- **Responses.**
  - `cards-NN.cares.json`, one per card file: a list of `{ "id", "add": [ { "fact", "strength": 1 to 3, "reason" } ] }`. It may be empty.
  - Optionally, `cares-table-suggestions.json`: a list of `{ "tag", "facts": [ { "fact", "strength" } ], "reason" }`.
- **Import.** `spa cares-import <set> --packet <dir> --provenance "<text>"` validates:
  - every card file has a response;
  - every id is a card in its file;
  - every fact is in `vocabulary.json`;
  - every strength is 1, 2 or 3;
  - no card repeats a fact;
  - no added fact equals one the card already cares about from Scryfall;
  - every reason is not empty;
  - every suggestion's `tag` is a Scryfall tag not already in `cares.json`, and its facts are in the vocabulary.

  It names every problem, one line each, and writes nothing on any problem. On success it writes `fixtures/otags/<code>.fable.json` (`{ "set", "provenance", "cards": [ { "id", "cares": [ { "fact", "strength", "reason" } ] } ] }`, only cards with additions, in collector order). It prints the count of additions and each suggestion, one per line.
- **Scoring.** `CaresTerm` merges the Fable file's cares with the Scryfall-derived ones, keeping the larger strength per fact. A set with no Fable file scores exactly as after SPA-054.
- **The prompt** is the Architect's; copy it into `cares-gaps-v1.md` word for word. A test pins the full text (lesson, SPA-047).
  > You are filling gaps in the "cares about" tags of a Magic: The Gathering set you have never seen played. Each card has facts (what it is and what it does), listed per card in `facts.json`, using the names defined in `vocabulary.json`, which also describes every Scryfall tag used. Some cards already care about facts, from Scryfall's community tags, shown in the `cares-NN.json` beside each card file, and the table below says which Scryfall tags mean caring about which facts. Read every card file. For each card, add a cares tag only when the card clearly rewards having cards with a fact and its existing cares tags do not already cover that idea; for example, a card that gets better for each artifact you control cares about `artifact`. Name the fact exactly as it appears in `vocabulary.json`, with a strength from 1 to 3 (1 a small bonus, 2 clearly better with it, 3 built around it) and a one-line reason. Do not add a cares tag for something the card only is or does. Most cards need none. If a Scryfall tag in `vocabulary.json` means caring about something (its name ends in "matters" or begins with "synergy") and is not in the table, you may suggest the facts it cares about in `cares-table-suggestions.json`. Write a `cards-NN.cares.json` for every card file, even when it is empty. Use only the files in this folder. Do not use the web or any tool other than reading these files and writing the response files.
- **Alterable.** The import checks are a list of check objects; a new check is one file.
- Use `syn`, with a hand-built otags file and cares table, for tests.
- Work on a local branch named exactly `SPA-055`. One Developer at a time. Never rewrite a pushed branch; keep scratch files out of the repository. JDK: README, Toolchain section. On Windows Git Bash, pass `C:/...` paths to the JVM.

## Acceptance criteria

1. `spa cares-packet trk --out <dir>` writes the files named in Background:
   - 7 card files, byte-identical to the grade packet's;
   - a `cares-NN.json` per card file, equal to SPA-054's cares for those cards;
   - a `vocabulary.json` holding every code fact and every otag present in trk with their ancestors, and no name tag;
   - the prompt text exactly as given;
   - byte-identical on a rerun.

   Tests pin this.
2. The packet passes `BlindCheck` and SPA-050's independence test.
3. On `syn`, each import check rejects its case, one line each, with exit 1 and nothing written:
   - a missing response file;
   - a card outside its file;
   - a fact outside the vocabulary;
   - strength 0 or 4;
   - a repeated fact;
   - a fact the card already cares about;
   - an empty reason;
   - a bad suggestion (a tag already in the table, or a fact outside the vocabulary).

   A valid set writes `<code>.fable.json` and prints the count and the suggestions. Tests pin each.
4. Scoring:
   - with a hand-built Fable file, a card gains a cares tag and scores with matching facts;
   - the larger strength wins when Scryfall and Fable give the same fact;
   - with no Fable file, `spa synergy-table --set trk` and `spa synergy-check --set trk` are byte-identical to before.
5. The seam: a test adds a test-only import check, with no other code change. `git diff <G-005 start> -- core/src/main fixtures/golden` lists no file. The gate is green.
