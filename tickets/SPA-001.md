# SPA-001: Set up the Kotlin toolchain, the gate script, the pre-push hook, and CI

**Goal.** G-001 deliverable 1: "A Gradle build with a `core` module (Kotlin, JVM, no Android dependencies), the gate script in `pipeline/gate/`, a pre-push hook that runs it, and a CI workflow that runs the same script. Green on an empty module before anything else is dispatched." Also goal-level criterion 1.

## Scope

- Files or modules expected to change:
  - `settings.gradle.kts`, `build.gradle.kts`, `gradle.properties`, `gradle/wrapper/**`, `gradlew`, `gradlew.bat`, `gradle/libs.versions.toml`
  - `core/build.gradle.kts`, `core/src/test/kotlin/spa/core/SmokeTest.kt` (the only test; no main sources)
  - `build-logic/**` (an included build holding the gate's Gradle plugin and its own unit tests; `buildSrc/` is acceptable instead)
  - `config/detekt/detekt.yml`
  - `pipeline/gate/run.sh`, `pipeline/gate/install-hook.sh`, `.githooks/pre-push`
  - `.github/workflows/gate.yml`
  - `README.md` (new "Toolchain" section only), `.gitignore` (only if the build creates files not already ignored)
  - `.gitattributes`: this machine has `core.autocrlf` enabled, so without it Kotlin and shell files check out with CRLF on Windows and LF on CI, and the format step can disagree between the two. Pin `* text=auto eol=lf`, with `*.bat` and `*.cmd` as `eol=crlf`.
- Not in scope:
  - Any application code in `core/src/main`. The module stays empty.
  - An `app` module, Compose, Paparazzi, or any Android plugin. Gate step 5 (UI and snapshot tests) is reported as `skipped` until an app module exists.
  - Fetching Scryfall data, fixtures, or anything from later tickets.
  - Installing the Android SDK.
- Dependencies this ticket may add (none unless listed). The format below is the one the gate's dependency audit parses in every ticket: one sub-bullet per coordinate, `group:artifact` for a library and `plugin:<plugin id>` for a Gradle plugin.
  - `plugin:org.jetbrains.kotlin.jvm`
  - `plugin:org.jetbrains.kotlin.plugin.serialization`
  - `plugin:com.ncorti.ktfmt.gradle`
  - `plugin:io.gitlab.arturbosch.detekt`
  - `plugin:org.jetbrains.kotlinx.kover`
  - `org.jetbrains.kotlinx:kotlinx-serialization-json`
  - `org.jetbrains.kotlin:kotlin-test-junit5`
  - `org.junit.jupiter:junit-jupiter`
  - `org.junit.platform:junit-platform-launcher`

Versions are the Developer's choice: the latest stable release of each at implementation time, recorded in `gradle/libs.versions.toml` and nowhere else. The catalog is the only place a dependency coordinate may appear; build scripts reference catalog aliases.

## Background the Developer needs

- The development machine is Windows 11 with git and the GitHub CLI, and no JDK or Gradle. Local commands run in Git Bash. CI runs on `ubuntu-latest`. The same script must pass in both.
- Use JDK 21 (an LTS release, and what CI installs). The human installs Temurin 21 with `winget install EclipseAdoptium.Temurin.21.JDK` before this ticket dispatches, because the installer needs an administrator prompt. If `java -version` does not report 21 in your shell, look under `C:\Program Files\Eclipse Adoptium\` and set `JAVA_HOME` for your session; if no JDK 21 is there, write that in the change note and stop. That is a bounce, not a failure. Record the vendor and exact version in the change note.
- Generating the Gradle wrapper needs a Gradle installation once. If `gradle --version` works, run `gradle wrapper --gradle-version <latest stable>`; if not, download the matching Gradle distribution zip into a temporary directory and run its `bin/gradle wrapper` from the repository root. The committed wrapper is what everyone uses afterwards.
- The gate contract is `pipeline/gate/README.md`. Step names in the verdict are exactly: `format`, `lint`, `compile`, `unit-tests`, `ui-tests`, `coverage`, `dependencies`.
- Implementation shape (the Developer may deviate if the criteria still hold): `pipeline/gate/run.sh` resolves the ticket id, runs `./gradlew check -Pticket=<id>`, and guarantees `gate-verdict.json` exists afterwards even when Gradle dies before writing it. The step logic, front-matter parsing, coverage computation from the Kover XML report, dependency-catalog diffing, and verdict serialization live in the `build-logic` plugin as plain Kotlin functions with unit tests. `check` runs the same steps in the same order, so `./gradlew check` is the gate.
- "Files the ticket touched" means files changed between `git merge-base origin/main HEAD` and the working tree, including uncommitted changes, filtered to `core/src/main/kotlin/**/*.kt`.

## Acceptance criteria

1. On a fresh clone with JDK 21 on `PATH` or `JAVA_HOME`, `./gradlew :core:test` completes green in Git Bash on Windows and on `ubuntu-latest`, with `core/src/main` empty and `SmokeTest` as the only test.
2. `pipeline/gate/run.sh` runs the seven steps in the README's order, stops at the first failing step, exits 0 on pass and non-zero on fail, and writes `gate-verdict.json` at the repository root with `ticket`, `commit` (short SHA), `result` (`pass` or `fail`), and `failures`, each failure having `step`, `file`, `line` (integer or null), `message`, and `reproduce`. Step `ui-tests` passes with a note `skipped: no app module` while no app module exists.
3. The ticket id is taken from `--ticket SPA-###` if given, else the environment variable `GATE_TICKET`, else the first `SPA-` followed by three digits in the current branch name, else `none`. With `none`, the coverage threshold is 0 and the dependency step requires `gradle/libs.versions.toml` to be unchanged from the merge base.
4. A Kotlin file that ktfmt would reformat makes `run.sh` exit non-zero with a single `format` failure naming that file, and no later step runs. Fixing the formatting makes the run pass.
5. A test that fails makes `run.sh` exit non-zero with a `unit-tests` failure whose `file` is the test source file, whose `line` is the failing assertion's line, and whose `reproduce` is a `./gradlew` command that runs only that test class.
6. The `coverage` step reads `coverage_threshold` from `tickets/<ticket>.md` front matter, computes Kover line coverage per touched file, and fails with one failure per file below the threshold, the message giving the file's percentage and the threshold. Zero touched files is a pass. Coverage is measured on `core/src/main/kotlin` only; `build-logic` and test sources are excluded.
7. The `dependencies` step fails, naming the coordinate, when (a) an entry added to `[libraries]` or `[plugins]` in `gradle/libs.versions.toml` since the merge base is not listed under "Dependencies this ticket may add" in the ticket file, or (b) any `*.gradle.kts` file outside `build-logic` contains a dependency coordinate as a string literal instead of a catalog alias. Proven by unit tests of the parsing and diffing functions and by one end-to-end scenario.
8. `pipeline/gate/install-hook.sh` sets `core.hooksPath` to `.githooks`. After running it, `git push` of a branch with a formatting failure is refused by `.githooks/pre-push` and the verdict file names the failure; a clean branch pushes.
9. `.github/workflows/gate.yml` runs on `pull_request` to `main` and on `push` to `main`, installs Temurin 21, runs `pipeline/gate/run.sh` with the ticket id derived from the head branch name, uploads `gate-verdict.json` as a workflow artifact on pass and fail, and the job fails when the gate fails. This ticket's own pull request shows the workflow green.
10. The unit tests in `build-logic` (front-matter parsing, verdict serialization, touched-file coverage from a Kover XML sample, dependency-catalog diffing, ticket-id resolution) run as part of `run.sh`, so a regression in the gate itself is red.
11. `README.md` has a "Toolchain" section stating the JDK requirement, how to run the gate, how to install the hook, where the verdict file is, and the dependency-list format tickets must use.

## Change note

- Changed: Gradle 9.8.2 wrapper, Kotlin 2.4.21, an empty `core` module with `SmokeTest`, and the `spa.gate` plugin in `build-logic` (an included build). `./gradlew check` runs seven gate tasks in contract order; a build service hears every task result, files failures under their step with file and line (ktfmt's message, detekt's XML, captured compiler errors, JUnit XML, Kover XML, the catalog diff), and writes `gate-verdict.json` when the build ends. `run.sh` writes a fallback verdict from the Gradle log when Gradle dies before the plugin loads. The root project formats and lints `build-logic` itself. Versions: kotlinx-serialization 1.12.0, JUnit 6.1.3, ktfmt-gradle 0.27.0 (kotlinlang style), detekt 1.23.8 (the latest stable under this plugin id; 2.x is alpha under `dev.detekt`), Kover 0.9.11. JDK: Eclipse Temurin 21.0.13+9, installed by the human with `winget install EclipseAdoptium.Temurin.21.JDK`.
- Not unit tested, and why: the Gradle wiring (`GatePlugin`, `GateService`, `GateTasks`, `Git`), `run.sh`, the hook, and the workflow need a real Gradle build, git, or GitHub. I ran these end to end on Windows: pass; bad format (one `format` failure, no lint task ran, passes after `ktfmtFormat`); failing core test (file, assertion line, `reproduce` reruns only that class and fails); broken `build-logic` test; core compile error; coverage below an 80% threshold; unlisted catalog library with a ticket and with `none`; a literal coordinate in `core/build.gradle.kts`; `build-logic` that does not compile (fallback verdict with file and line); malformed `GATE_TICKET` and `--ticket`.
- Chose not to: auto-detect `JAVA_HOME`; add a Gradle TestKit suite for the wiring; pin a daemon JVM. `:build-logic:test` can execute before the format step finishes, because Gradle runs included builds on their own schedule; it ignores failures inside the main build and the `unit-tests` step reads its XML, so reported order is still the contract's. The pre-push hook gates the working tree, not exactly the pushed commit.
- Next ticket should know: a scratch or new file must pass detekt's default rules too (`FunctionOnlyReturningConstant` flags `fun f() = 1`). Coverage keys a file by its `package` line, as Kover does. `ui-tests` fails once an `:app` project exists, until a ticket adds that step. detekt 1.23.8 and ktfmt-gradle 0.27.0 use Gradle APIs deprecated for Gradle 10, so every build prints a deprecation notice; it is theirs, not ours.
