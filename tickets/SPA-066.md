- From the design brief, the two questions (use these sentences as the first paragraph of each prompt file, word for word):
  - Interaction (`interaction`, title `Interaction`): "How much removal and interaction is here, and what does it answer? Say how many removal spells and other interaction the pool has, overall and in each color pair, of which kinds, against the set baseline, and whether it can deal with the threats the set's format brief describes."
  - Bomb Assessor (`bombs`, title `Bombs and splashes`): "Which cards win games on their own, and do they justify a color commitment or a splash? Name the pool's strongest cards, say which are build-arounds, and say what it costs to play each one: its colors, and whether a splash can support it."
- Metric pointers: `/removalTotal`, `/interactionTotal`, `/pairs/WU/removal`, `/pairs/WU/interaction`, `/byColor/W/interaction`, `/pairs/WU/splashCandidates/count`. `Tag` has `REMOVAL`, `COUNTER`, `BOUNCE`, `TRICK` (and `FIXING`, which is not interaction); `SplashReason` is `REMOVAL` or `RARE_OR_MYTHIC`.
- Design this ticket fixes (do not redesign). Each agent is an `object` implementing `AnalysisAgent`; `unavailable` returns null:
  - **interaction** `numbers`: `NumberTables.fromMetrics` with patterns `/removalTotal`, `/interactionTotal`, `/pairs/*/removal`, `/pairs/*/interaction`, `/byColor/*/interaction`. `facts`: the line `Cards by tag:` then one line per tag in the order REMOVAL, COUNTER, BOUNCE, TRICK: `<TAG> (<copies> copies): <name> x<copies>, ...` over the pool's nonland cards the tagger tags (a card with two tags appears under both; names sorted; `none` for a tag with no card, with `(0 copies)`).
  - **bombs** `numbers`: a `NumberTable` with, for each candidate card, the entry key `/grades/<name>` (the card's full name with `~` written `~0` and `/` written `~1`), value the card's grade, no `typical`; then the entries `NumberTables.fromMetrics` gives for `/pairs/*/splashCandidates/count`. A candidate is a distinct nonland card of the pool that has a grade and is rare or mythic (by the printing's rarity) or has a grade of 4.0 or more; the 25 best by grade (then name) if more. `facts`: the line `Candidates:` then one line per candidate, best grade first, ties by name: `<name> (<rarity lowercase>, colours <letters in WUBRG order or colourless>)`; then, for each pair that has splash candidates, `Splash candidates <pair>: <name> (<colour>, <reason lowercase with underscores as spaces>), ...`.
  - **Prompt files**: at most 30 lines; the question above as the first paragraph; then, in your own words, what the table and facts hold, what to compare with the baseline (interaction) or how to weigh a card's grade, cost and colours against the pool's depth (bombs), and the findings a player acts on. No card name, set name or set code, and no digit.
  - `AnalysisAgents.ALL` becomes the SPA-065 list followed by `InteractionAgent`, `BombAgent`. Add to `fixtures/agents/review.json` `agents`, after the existing three, `{ "id": "interaction", "enabled": true, "maxTokens": 3000, "prompt": "v1" }` and the same for `bombs`.

## Acceptance criteria

1. Each agent has the id and title above and `unavailable(input)` is null for any input.
2. `InteractionAgent.numbers` holds exactly the entries `NumberTables.fromMetrics` gives for its patterns (keys, values, `typical`), with `/removalTotal`, `/interactionTotal` and `/pairs/WU/removal` checked against values worked out by hand for a hand-built pool.
3. `InteractionAgent.facts` equals the specified lines for a hand-built pool with a card of each tag, a card with two tags (under both), a tag with no card (`none`, 0 copies), a card with two copies, and a land (left out).
4. `BombAgent.numbers` holds the grade entries for the candidates and the splash count entries: a rare with grade 2.0 is a candidate; a common with grade 4.0 is a candidate; a common with grade 3.5 is not; an ungraded rare is not; a land is not; a name containing `/` is keyed with `~1`; with 26 candidates only the best 25 are kept (tie broken by name).
5. `BombAgent.facts` equals the specified lines on that pool, including a colourless candidate (`colours colourless`), a multi-colour candidate in WUBRG order, and a pair with and without splash candidates.
6. Each prompt file exists, is at most 30 lines, begins with its question sentence exactly, and contains no digit.
7. `AnalysisAgents.ALL` lists the five ids in the order `colour-depth`, `curve`, `mana`, `interaction`, `bombs`.
8. `fixtures/agents/review.json` stays valid JSON and its `agents` array holds the five entries in order (Acceptance Tester scenario below).
9. The gate is green: format, lint, compile, unit tests, coverage 80 or more on the touched files, no new dependency.

## Change note

Added `InteractionAgent` and `BombAgent` (objects, `unavailable` null), their `interaction-v1.md` and `bombs-v1.md` prompts, the two entries in `AnalysisAgents.ALL` and in `fixtures/agents/review.json`; criteria 1-7 are covered by unit tests (red commit first), 8 is the Acceptance Tester scenario (the node command prints the expected line), 9 is the gate.
Choices: both agents tag from the faces' type line and oracle text unioned, as the engine does, and merge printings by oracle id; a card in several printings is one bomb candidate with its best grade. Colours in the candidate lines are letters with no separator (`WUG`). `Candidates:` stands alone when the pool has none; a tag's `(N copies)` always reads `copies`, even for one.
`NumberTables`/the flattener's escape is `internal` to `core`, so `BombAgent` has its own two-line escape for `~` and `/`; a later ticket could expose the core one.
Red commit note: the red tests failed by compile error (the agents did not exist); one test line (`Printing.id` should be `scryfallId`) was fixed in the green commit.
Nothing here needs a device, the network or a model; the prompt wording is judged by the Acceptance Tester only through criteria 6 and 8.
