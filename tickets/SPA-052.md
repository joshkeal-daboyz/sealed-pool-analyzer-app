# SPA-052: Fable review pass for synergy tags

**Goal.** The owner said on 2026-11-05: "Perhaps we should leverage Fable to look over the cards and ensure the proper tags are applied to each card." This ticket adds a third, review pass after pass 2:
- `spa tags-review-packet` writes a packet;
- a fresh Fable agent writes corrections, each with a reason;
- `spa tags-review-import` validates the corrections, applies them to the tag file and records them.

The Architect runs the reviews after merge.

## Background the Developer needs

- Read the G-005 Architect note "Owner: Perhaps we should leverage Fable…", SPA-047 (packets, import check list), SPA-051 (facts, `suppliedBy`) and `TagFiles`.
- **Packet.** `spa tags-review-packet <set> --out <dir> [--tags <file>] [--prompt v1]` takes the tag file from `--tags`, by default `<data>/tags/<code>.json`. It writes:
  - `instructions.md`: the review prompt, then the axes (id, name, definition, `suppliedBy`), then the brief and theme counts as in the tags packets;
  - the same `cards-NN.json` files as the grade packet;
  - `facts.json`, as SPA-051 writes it;
  - `tags-NN.json` beside each card file, holding that file's cards' current roles and partners;
  - `review.schema.json` and `fact-suggestions.schema.json`.

  The packet is byte-identical across runs. It is blind under `BlindCheck`, and it contains no check id and not the word `synergy-checks` (SPA-050's independence test covers it).
- **Responses.**
  - **`cards-NN.review.json`** beside each card file, a list of corrections. Each is `{ "id", "action", "axis"?, "role"?, "partner"?, "strength"?, "reason" }`. `action` is one of:
    - `add-role` (axis, role, strength);
    - `remove-role` (axis, role);
    - `set-strength` (axis, role, strength);
    - `add-partner` (partner, strength);
    - `remove-partner` (partner).

    An empty list is valid, and every card file needs a review file.
  - **`fact-suggestions.json`**, optional: a list of `{ "fact", "rule", "examples": [card ids], "reason" }`.
- **Import.** `spa tags-review-import <set> --packet <dir> --provenance "<text>"` reads the tag file the packet was built from (the packet records its path and a hash of its bytes). It applies every correction in file order, then card order, then validates:
  - the target card is in the packet's file;
  - `remove-role`, `set-strength` and `remove-partner` target something that exists;
  - `add-role` and `add-partner` do not duplicate;
  - the reason is not empty;
  - the result passes every pass-2 check (SPA-047 and SPA-051).

  It names every problem, one line each, and writes nothing on any problem. On success it writes `<data>/tags/<code>.json` with the same set, axes and provenance as before, plus a `review` block holding the review provenance, the applied corrections with their reasons, and a count by action. It then prints that count and every fact suggestion, one per line. If the tag file changed since the packet was built (the hash differs), it stops with one line.
- **The prompt** is the Architect's; copy it into `tags-review-v1.md` word for word. A test pins the full text (lesson, SPA-047).
  > You are reviewing the synergy tags of a Magic: The Gathering set you have never seen played. The set's axes, and the facts that supply each axis, are listed below; each card's facts are in `facts.json`, and the current tags for each card file are in the `tags-NN.json` beside it. Read every card file and its tags. For each card, check its roles and partners against its rules text: add a role the card clearly has but lacks, remove a role it does not have, change a strength that is clearly wrong, and add or remove a named partner. A card's facts already supply the axes listed for them, so do not add an enabler role that only repeats a fact. Make a correction only when you are confident; most cards need none. Give each correction a one-line reason. If several cards should share a fact that the fact list lacks, describe it in `fact-suggestions.json`, with example cards. Write a `cards-NN.review.json` for every card file, even when it is empty. Use only the files in this folder. Do not use the web or any tool other than reading these files and writing the response files.
- **Alterable.** Each correction action is its own class behind one interface, in a list. A new action is one file.
- Use `syn` with a hand-built tag file for tests.
- Work on a local branch named exactly `SPA-052`. One Developer at a time. Never rewrite a pushed branch; keep scratch files out of the repository. JDK: README, Toolchain section.

## Change note

- **What changed.** New `agent/.../tags/review/`: the five actions (one class each, listed in `ReviewActions.ALL`), `ReviewFiles` (reads the review files and suggestions; shape only), `ReviewApply`, `TagReviewPackets`, `TagReviewImport`, `ReviewPrompts`. Resources: `tags-review-v1.md` (the ticket's quoted line copied by `grep`/`sed`, pinned whole in `ReviewPromptsTest`), `review.schema.json`, `fact-suggestions.schema.json`, and an optional `review` block in `tags.schema.json`. `TagFile` gets a nullable `review`, left out of the JSON when null, so the committed files write back byte for byte. The CLI adds `tags-review-packet` and `tags-review-import`, wired in `Main.kt` with help text. README and `fixtures/tags/README.md` describe both.
- **Choices.** The packet records the tag file in an extra file, `tag-file.json` (`path`, absolute and normalized, and `sha256`), so packet and import must run from the same checkout. Corrections apply by review file (card-file order), then by the card's place in its card file; a card's own corrections keep the order given. The pass-2 checks run on the corrected tags, each card named against its review file. `counts` lists every action of the list, zeros included. A `review` block the tag file already had is replaced, not appended. The import ignores `tags-NN.json`: the hash-guarded tag file is the source. `review.schema.json` is a static resource listing the five actions. A new action is one file plus its `ReviewActions.ALL` entry, and needs a schema entry only so the reviewer is told about it; the import never reads that schema. The tag schema's `action` is a pattern, not an enum, so a test-only action validates.
- **Outside the listed files, kept small.** `TagPackets.factsFile` and `TagPacketText.cardsLine` and `range` went from private to internal, so the review packet reuses them (`facts.json` byte-identical, same cards line). `TagFile.kt` holds the review types. `SynergyCheckIndependenceTest` now also builds the review packet and lists `tags-review-v1.md` among the resources it scans.
- **Red commit ab5388b.** agent: 356 tests, 21 failing. cli: 376 tests, 40 failing. Every failure is in the new classes, plus 2 of the 4 in `SynergyCheckIndependenceTest`. A few new tests passed at red: the 20-axis v2 round trip (the schema already allowed 20 axes; the test closes SPA-051's surviving probe), 21 axes rejected, the committed trk file writing back byte for byte, the action field sets, and the schema-rejection test (true at red only because the old schema rejected any `review`). After the green code I added `TagReviewPacketsTest` and `TagReviewImportTest` in `agent`. The gate measures each module's coverage only with that module's own tests, and these two classes were tested only through `cli`. The new tests also cover a card named in the other card file's review, which `syn`'s single card file cannot show. Final counts: agent 371 tests, cli 377, 0 failing.
