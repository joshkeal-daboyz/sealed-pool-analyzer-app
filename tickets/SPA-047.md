# SPA-047: Synergy tagging packet, import and tag files

**Goal.** G-005 deliverable 7 and criterion 8: the code that lets a Fable agent tag every card in a set for synergy, and validates and stores the result. This covers two packet commands, an import command and a tag file format. The Fable runs themselves are the Architect's, after merge, as for grading in G-003 and G-004; `trk` goes first, before 17Lands publishes `trk` data.

  - `cli/src/main/kotlin/spa/cli/`: the `tags-packet` and `tags-import` commands, wired in `Main.kt`'s handler map and help text, with tests

## Background the Developer needs

- Read G-005 deliverable 7 (axes, roles, named partners, the card with itself), criterion 8 and the Constraints. Read SPA-033's ticket and `agent/.../grader/` (`GradingPacket`, `GradingPool`, `PacketCard`, `PacketThemes`, `GradeImport`), and reuse them: the same pool, the same card format, the same 50 cards per file, the same byte-identical packet.
- **Two passes, because the roles need the axes first.**
  - **Pass 1, the axes.** `spa tags-packet <set> --out <dir>` writes:
    - `instructions.md`: `tags-axes-v1.md`'s text, then the set's format brief rendered as the grading packet renders it, then SPA-036's theme counts as in a v2 grading packet;
    - `cards-NN.json`, exactly as the grading packet writes them;
    - `axes.schema.json`.

    The agent writes `axes.response.json`, a list of `{ "id", "name", "definition" }`. `id` is lowercase letters, digits and hyphens; there are 3 to 15 entries, and the ids are distinct.
  - **Pass 2, the roles.** `spa tags-packet <set> --axes <axes.response.json> --out <dir>` validates the axes file first (one line per problem, exit 1, nothing written). It then writes:
    - `instructions.md`: `tags-roles-v1.md`'s text, then the axes as a list (id, name, definition), then the brief and theme counts as above;
    - the same `cards-NN.json` files;
    - `response.schema.json`.

    The agent writes `cards-NN.response.json` beside each card file: a list of `{ "id": card id, "roles": [ { "axis", "role": "enabler" | "payoff", "strength": 1 | 2 | 3 } ], "partners": [ { "id": card id, "strength": 1 | 2 | 3 } ] }`. `roles` and `partners` may be empty.
- **The import.** `spa tags-import <set> --packet <dir> --provenance "<text>"` reads the pass-2 packet, its axes and every response. It checks:
  - every pool card appears exactly once and no unknown id appears;
  - every axis is one of the packet's axes;
  - each role is `enabler` or `payoff`, and each strength is 1, 2 or 3;
  - a card does not repeat the same axis and role;
  - every partner id is a card in the pool (the card itself is allowed), with at most 5 partners and none repeated.

  It names every problem, one line each, and writes nothing on any problem. On success it writes `fixtures/tags/<code>.json`: `{ "set", "provenance", "axes": [...], "cards": [ { "id", "name", "roles", "partners" } ] }` in collector order. The file is validated against `tags.schema.json` and read back by a `TagFiles.read` that the next ticket uses.
- **The prompts** are written by the Architect; copy them into the two resource files as given, word for word.
  - `tags-axes-v1.md`:
    > You are reading a Magic: The Gathering set you have never seen played, to find its synergies for Sealed. Read every card file in this folder first. Then name the set's synergy axes: the things some cards supply and other cards reward, such as a kind of token, a counter, a card type, a creature type, sacrificing, a graveyard or a mechanic of this set. Give between 3 and 15 axes. Include a creature type or card type only if at least three cards reward it. Leave out general strengths that every set has, such as removal, card draw or big creatures; they are not synergy. For each axis give an id (lowercase words joined by hyphens), a short name, and a one-line definition of what counts as supplying it. Use only the files in this folder. Do not use the web or any tool other than reading these files and writing `axes.response.json`, which must match `axes.schema.json`.
  - `tags-roles-v1.md`:
    > You are tagging every card of a Magic: The Gathering set you have never seen played, for Sealed synergy. The set's axes are listed below. Read every card file in this folder first. For each card, list its role on each axis it touches.
    > - **enabler**: it supplies the axis. Strength 1 is incidental, 2 is a clear supplier, and 3 is a core supplier (repeatable, or several at once).
    > - **payoff**: it rewards the axis. Strength 1 is a small bonus, 2 means it is clearly better with the axis, and 3 means it is built around the axis.
    >
    > A card can be both on the same axis. Most cards touch no axis or one; do not stretch. Then list up to 5 named partners: specific cards in this set that this card works with beyond the shared axes, such as a card that names another, or two cards that form a combo, each with a strength from 1 to 3. A card may name itself when its copies help each other beyond the axes. Give every card exactly once, in its own file's response, matching `response.schema.json`. Use only the files in this folder. Do not use the web or any tool other than reading these files and writing the response files.
- **Blind.** Neither packet contains a 17Lands field, a win rate or review text. As in G-003 criterion 5, a test inspects generated packets for the same forbidden words that the grading packet test uses.
- **Alterable** (G-005 Constraints). The prompt version is a parameter (`--prompt v1` by default, the file named by version), so a v2 prompt is a new resource file, not a code change. The import's checks are a list of check objects, so a new check is one file.
- Use the synthetic set `syn` for hand-built response tests, as SPA-033 did.
- Work on a local branch named exactly `SPA-047`. One Developer at a time. Never rewrite a pushed branch; keep scratch files out of the repository. JDK: README, Toolchain section.

## Acceptance criteria

1. `spa tags-packet trk --out <dir>` writes `instructions.md`, `axes.schema.json` and `cards-01.json` to `cards-07.json`, holding 336 cards. Running it twice gives byte-identical files. The card files are byte-identical to `spa grade-packet trk`'s card files. A test pins this. The pools are `msh` 276 cards (6 files), `hob` 188 (4), and `fra` 280 (6).
2. Pass 2 with a valid axes file writes the axes into `instructions.md` in the given order, plus `response.schema.json`. A bad axes file is rejected, one line per problem and exit 1, for each of these: fewer than 3 axes, more than 15, a duplicate id, an id with a capital or a space, and a missing definition. Tests pin each case.
3. Neither packet holds any forbidden word, and the instructions say to use no web or other tool. A test pins this for `trk` pass 1 and pass 2.
4. `spa tags-import syn` on a hand-built valid response set writes a tag file that validates against the schema and reads back equal through `TagFiles.read`. Each of these is named on its own line, with exit 1 and nothing written:
   - a missing card;
   - a card given twice;
   - an unknown card id;
   - an unknown axis;
   - a bad role;
   - strength 0 or 4;
   - a repeated axis and role;
   - a partner outside the pool;
   - six partners;
   - a repeated partner.

   A card naming itself as a partner imports. Tests pin each case.
5. The seam: a test adds a test-only import check to the list and sees it reject a response, with no other code change. `--prompt v9`, which has no such file, is one line and exit 1. `git diff <G-005 start> -- core/src/main fixtures/golden` lists no file. The gate is green.
