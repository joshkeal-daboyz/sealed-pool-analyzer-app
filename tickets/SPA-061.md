# SPA-061: Check that higher builder scores go with higher win rates, with spa score-backtest

**Goal.** G-005 is closed (all tickets integrated and archived, 2026-11-06). This is its follow-up, the owner's words of 2026-11-06: "The measure of whether a deck is strong is results: whether higher builder scores go with higher win rates (a score-against-results check on held-out builds)." It adds `spa score-backtest`, which scores each real build of a 17Lands Sealed file with the deck builder and reports how the score relates to the player's win rate, for the builder's weights and for plain set grades.

## Background the Developer needs

- **Files to read** (nothing else in the repository): `agent/src/main/kotlin/spa/agent/deckbacktest/` (`BacktestBuilds`, `BacktestBuild`, `BacktestReport`, `Backtest`, `Measure`), `agent/.../build/` (`DeckBuilder`, `BuildSetup`, `Deck`, `DeckCard`, `DeckWeights`), `agent/.../backtest/Spearman.kt` and `SpearmanTest.kt`, `cli/src/main/kotlin/spa/cli/` (`DeckBacktestCommand` as the pattern, `BuildSession`, `Main.kt`), the tests beside them for how `syn` sets and hand-built Sealed files are made, and `fixtures/weights/README.md`, `fixtures/weights/deck-baseline.json`, `fixtures/weights/deck-tuned.json`.
- **What is checked.** The Sealed file (17Lands public data, never committed) has one row per game. A build is one `(draft_id, build_index)`, read once from its first row. `user_game_win_rate_bucket` on that row is the player's win rate over their games in steps of about 0.02 (the Architect's script, 2026-11-06: in `hob` the observed win rate of each bucket's games matches the bucket to within 0.02 from 0.30 to 0.88), so it is the result for the build. It is a player's result, so it carries the player's skill as well as the deck; the README says so. For each build the command scores **the deck the player registered** with the builder's parts, `DeckBuilder.evaluate(setup, spells, landCount)` (`ScoredDeck.total`), with no search. It does that twice, with `--weights` (default `fixtures/weights/deck-tuned.json`) and with `--baseline` (default `fixtures/weights/deck-baseline.json`, which scores a deck as the sum of its spells' set grades), and reports for each the rank correlation between score and bucket. The question the numbers answer: does the full builder rank real builds by results better than set grades alone?
- **Which builds.** Every build with a numeric bucket, not only strong ones (the existing reader keeps buckets of 0.60 or more only). Counted by the Architect's script before any card is resolved: `hob` 13,968 builds, 13,913 with a bucket; `msh` 12,019 with a bucket of 12,090; `fra` 15,205 with a bucket of 15,331. A build is skipped, and counted, under the first reason that applies: a blank bucket; one main colour or five (`DeckShape.of` is null); a card name that resolves to no card of the set (`unresolved`); no nonland card inside the player's colours (`no-choice`); a splash that is also a main colour or more than two splash colours (`BacktestBuild.config` is null, `no-config`); a registered deck (deck counts, lands included) that is not exactly 40 cards (`not-40`); a registered nonland card that is not among the setup's candidates for the player's configuration (`off-colour`). The Developer runs the case and rules on any other edge, and records each ruling in the change note.
- **The registered deck.** The player's configuration is `BuildConfig(main, splash)`. The spells are the registered nonland cards, one `DeckCard` per copy as `DeckSearch` forms them (read how), taken from the candidates of `session.setup(pool, config)`; the land count is the registered count of land cards, basics included. The builder's own mana split for that colour set is used; the player's basics split is not read.
- **The statistic, exactly.** Spearman rank correlation between score and bucket, using the existing `Spearman` (no second copy), over the scored builds, plus `se`, the rough standard error `1 / sqrt(n - 1)`. Also the top-quarter and bottom-quarter means of the bucket: sort by score ascending with ties kept in file order, let `q = max(1, n / 4)` (integer division), the bottom quarter is the first `q` builds and the top quarter the last `q`, and `gap` is top minus bottom. With fewer than 4 scored builds every number prints as `-`.
- **`spa score-backtest <sealed-file> --set <code> [--limit <n>] [--weights <file>] [--baseline <file>] [--tags <file>] [--otags <file>] [--data <dir>]`.** `--limit n` keeps n builds spread evenly through the kept builds in file order (build i is the one at position `i * kept / n`), as in `spa deck-backtest`; without it, all. The owner's standing rule of 2026-11-06 is 30 builds per set for runs by the Architect; the command itself has no default limit. A gzipped or plain file. Output, in this order, one line each:
  - `read <n> builds with a bucket; skipped one-colour <a>, five-colour <b>, unresolved <c>, no-choice <d>, no-config <e>, not-40 <f>, off-colour <g>`
  - `scored <n> builds`
  - `builder: spearman <r> se <s> top-quarter <mean> bottom-quarter <mean> gap <g>`
  - `baseline: ` the same numbers
  - `time <seconds> s`

  `r`, `s` and the means print with three decimals. A missing file, an unknown set, a bad number or a bad weights file is one line, exit 1.
- **Alterable.** The statistic is its own small class behind an interface, in its own file, so another can be added with one list entry, as the measures of `spa deck-backtest` are.

## Acceptance criteria

1. **Reading all buckets.** On `syn`, hand-built Sealed files prove: a build of bucket 0.30 is kept when the minimum is 0 and skipped at the default; 0.60 kept and 0.59 skipped at the default (unchanged); a blank bucket is skipped and counted; the kept build carries its bucket; every `spa deck-backtest` test passes unchanged.
2. **The statistic.** Hand-built score and bucket lists, with no builder in the loop: scores that rise with the bucket give 1.000 and the reverse gives -1.000; two tied scores get the average rank; `n = 8` gives quarters of 2 builds, and `n = 5` gives quarters of 1; `se` is `1 / sqrt(n - 1)`; fewer than 4 builds print `-`.
3. **The scored deck.** On `syn`, a hand-built build's score with the baseline weights equals the sum of the grades of its registered spells (computed by hand in the test); with the default parts it equals `DeckBuilder.evaluate` called on those same cards. The skip reasons `not-40`, `off-colour`, `no-config` and `no-choice` each have a hand-built build, and the counts in the `read` line add up to the builds read.
4. **The command.** On `syn` with a hand-built file, `spa score-backtest` prints the lines of Background in order and the same numbers on every run; `--limit` takes evenly spread builds; bad inputs are one line, exit 1.
5. **Real data (Acceptance Tester).** On the three files, `--limit 30` finishes, prints the five lines, the `read` line starts with the pinned count of builds with a bucket, `spearman` and the means are in range (-1 to 1, 0 to 1), and two runs print the same numbers apart from `time`.
6. **The seam, and no change elsewhere.** `git diff 2962b0f -- core/src/main fixtures/golden` lists no file. A test adds a test-only statistic to the list and sees it in the output with no other code change. The gate is green.
7. **Speed.** The change note records the time for the whole `hob` file (no `--limit`) on this PC, so the Architect can decide whether to run more than 30 builds.

## Change note

Added `spa score-backtest`: `BacktestBuild.bucket`, `BacktestBuilds.read(..., minBucket)` and `BacktestSelection.blank` (blank buckets counted, not printed); the new `deckbacktest/score/` package (`ScoreStatistic` with `SpearmanStatistic` and `QuarterStatistic` in `ScoreStatistics.ALL`, `RegisteredDeck`, `ScoreReport`); `ScoreBacktestCommand`, `Main.kt` wiring and help, a README section. `DeckBacktestCommand.read` gained a defaulted `minBucket`; its output is unchanged. Not done: nothing in scope was left out; no threads (the command scores only the registered deck).
Rulings: the spells are the registered nonland cards summed by oracle id and looked up in each session's `setup.spells`; a build is skipped for both scorers if either skips, in the order no-config, not-40, off-colour. With `--limit`, the `read` line counts the reader's skips over the whole file and the scorer's skips over the n builds used, so the counts add up to the builds read only without `--limit`. A statistic with no number (all scores equal) prints `-` for `r` but still prints `se`. The gate measures coverage of `agent` main files too, so the agent has its own tests (`RegisteredDeckTest`, `ScoreStatisticsTest`, `BacktestBucketsTest`).
Criterion 7, this PC, `cli/build/install/spa/bin/spa score-backtest .cache/17lands/game_data_public.HOB.Sealed.csv.gz --set hob` with no `--limit`: 71.6 s wall, `time 69.3 s`; `--limit 30` takes 0.7 s. It read 13,913 builds and scored 4,979 (not-40 1,202, off-colour 7,676, no-config 24, one-colour 30, five-colour 2); builder spearman 0.129, baseline 0.167, se 0.014.
For the Architect: off-colour is 55% of `hob` builds. It is not the splash pip limit (a copy of `deck-tuned.json` with `maxPips` 9 gives the same counts on 300 builds), and the cause is not found; it may bias what the check sees. Cannot be unit tested: the real-data numbers (needs the 17Lands files, criterion 5, Acceptance Tester).
