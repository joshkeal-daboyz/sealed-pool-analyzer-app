# SPA-010: Pin analyze output for every fixture pool and hand-check three of them

**Goal.** Goal-level criterion 5: "Golden-file tests pin the metric engine's output for every fixture pool, and three fixtures have their key counts (cards per color, removal count, creature count per pair, land recommendation) checked by hand and recorded in the test." This is the last ticket of G-001.

## Scope

- Files or modules expected to change:
  - `fixtures/golden/<fixture file name>.json` for every entry in `fixtures/pools/manifest.json`, `fixtures/golden/README.md`
  - `cli/src/test/kotlin/spa/cli/GoldenTest.kt`, `cli/src/test/kotlin/spa/cli/HandCheckedPoolsTest.kt`
  - `cli/build.gradle.kts` (pass the `updateGoldens` project property to tests)
- Not in scope:
  - Changing any metric, parser, sampler, or CLI behavior. A discrepancy found while hand-checking is a bounce to the Architect with the fixture, the field, and the two numbers; do not "fix" the engine here.
  - Regenerating fixtures or baselines.
- Dependencies this ticket may add (none unless listed):
  - (none)

## Acceptance criteria

1. `GoldenTest` runs `Main.run` for every manifest entry with its declared set and format, strips the volatile fields `tool.version` and `pool.file`, and compares the remaining JSON byte-for-byte (after line-ending normalization) with `fixtures/golden/<name>.json`. A missing golden file fails the test with a message naming the command to regenerate.
2. `./gradlew :cli:test -PupdateGoldens=true` rewrites every golden file from the current output and the test then passes; without the property, nothing is written. The committed goldens were produced this way and the gate is green.
3. `HandCheckedPoolsTest` covers `trk-manabox-01.csv`, `trk-text-01.txt`, and `trk-collector-01.txt`. For each, the test asserts literal values for: cards per color bucket (`W, U, B, R, G, MULTI, COLORLESS`) and lands; `removalTotal`; `creatures` for all ten pairs; and `landRecommendation` for the two pairs with the most cards. The expected numbers are derived by the Developer from the fixture file and the Scryfall cache by hand (listing the cards per bucket in a comment block above each assertion group), not by copying engine output. Forty or more literal assertions in total.
4. Each hand-derived list in the comments names every card counted, so the Acceptance Tester can recount from the fixture file and the cache without running code.
5. `fixtures/golden/README.md` states what the goldens pin, that they change whenever the cache, brief, baseline, fixtures, or engine change, and that updating them is done only by a ticket that says so in its change note.

## Change note

- `GoldenTest` runs `analyze` for all 26 manifest entries with their set and format, strips `tool.version` and `pool.file`, and compares with `fixtures/golden/<pool file>.json`; `-PupdateGoldens=true` (passed as the `spa.updateGoldens` system property and a test-task input) rewrites them. It also fails on a golden file with no manifest entry. The committed goldens were written that way, and a second run leaves the tree unchanged.
- `HandCheckedPoolsTest` asserts 105 literals over the three pools: buckets, basic and nonbasic lands, nonland total, removal, creatures and cards for all ten pairs (cards per pair show which two pairs are largest), and the land split for those two. I derived them from the pool files and the cache, using a throwaway Node script to list each card's colors, types, and costs, and judged removal by reading oracle text against the tagger's rules. They all matched the engine on the first run, so there is nothing to bounce.
- Chose not to: compare goldens structurally (they are byte comparisons, as the criterion says), or make update mode delete stray goldens (the stray check fails instead).
- Next ticket: any change to the cache, briefs, baselines, fixtures, or engine now shows up as golden diffs; the ticket must say it updates them.
