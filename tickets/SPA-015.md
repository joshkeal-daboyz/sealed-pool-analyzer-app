# SPA-015: Bundle the trk set data in the APK and build the app's import path

**Goal.** G-002 deliverable 2: "The `trk` and `sds` Scryfall caches, `fixtures/briefs/trk.json`, and `fixtures/baselines/trk.json` packaged into the APK at build time, straight from `fixtures/` (one source of truth, no hand-made copies), and loaded on the device through `core`'s existing loaders." Also the engine half of goal criterion 4, and the import-failure classification in the spec's Pool screen section. There is no screen in this ticket. It gives every later app ticket one tested way to turn text into results.

## Scope

- Files or modules expected to change:
  - `app/build.gradle.kts`: a build step that copies the set data from `fixtures/` into generated assets, and fails the build if any file is missing
  - `app/src/main/kotlin/spa/app/data/**`: `SetData`, which copies the bundled assets to app storage and loads them through `core`
  - `app/src/main/kotlin/spa/app/importing/**`: `PoolImporter`, `ImportOutcome`, `ImportFailureKind`, `PoolSource`
  - `app/src/test/kotlin/spa/app/data/**`, `app/src/test/kotlin/spa/app/importing/**`
- Not in scope:
  - Any screen, composable, ViewModel, or navigation (SPA-016).
  - Remembering the pool across launches (SPA-022).
  - Share and Open with intents (SPA-021), and the system file picker (SPA-017).
  - Any change in `core/`, `cli/`, or `fixtures/`.
  - Bundling `syn` (Decided 6).
- Dependencies this ticket may add (none unless listed):
  - `org.jetbrains.kotlinx:kotlinx-coroutines-android`
  - `org.jetbrains.kotlinx:kotlinx-coroutines-test`

## Acceptance criteria

1. The debug APK holds `assets/setdata/scryfall/trk/cards.json`, `companions.json`, `set.json`, and `fetched-at.txt`, the same four under `assets/setdata/scryfall/sds/`, `assets/setdata/briefs/trk.json`, and `assets/setdata/baselines/trk.json`. Each is byte-identical to its file under `fixtures/` (same SHA-256 after `unzip -p`). The APK holds nothing under `assets/setdata/scryfall/syn/`. `git ls-files app` lists none of these files: they are copied at build time, not committed.
2. With `fixtures/scryfall/trk/fetched-at.txt` renamed away (a scratch change), `./gradlew :app:assembleDebug` fails with a message naming that file. With it restored, the build passes.
3. `SetData` copies the bundled files to a folder under `Context.filesDir` on first use, then loads them through `CardIndex.load`, `BriefLoader`, and `Baseline.decode`. A Robolectric test, using the app's real merged assets, asserts that the loaded index has 581 `trk` printings and 30 `sds` printings, and that the baseline has `setCode` `trk`, `kits` 2000, and `seed` 20261106. Those three values are read from `fixtures/baselines/trk.json` in the test. A second load in the same process returns the cached data without reading the files again, and a second process start (a new `SetData` over the same `filesDir`) does not copy again. Both are shown by test seams. Loading runs off the main thread (a `suspend` function on an IO dispatcher).
4. `PoolImporter.import(text, format, source)` takes the pool text, a `PoolFormat` or null for auto-detection, and a `PoolSource` (a file name, or pasted). It returns `ImportOutcome.Success` with the `PoolParser` result, the `MetricEngine` metrics, the format used, and the source, or `ImportOutcome.Failure` with an `ImportFailureKind`, the source, and the unresolved lines. It calls `PoolParser.parse(text, index, format, brief.kitTemplate)` exactly as `AnalyzeCommand` does. `PoolImporter.detect(text)` returns `PoolParser.detect(text)`.
5. For each of the 23 `trk` fixtures in `fixtures/pools/manifest.json` (the test asserts the count is 23), importing the file's text with format null through `PoolImporter`, backed by `SetData` over the bundled assets, gives `Success`. `MetricEngine`'s output, flattened with `MetricFlattener.flatten`, has exactly the numeric pointers of the golden file's `/metrics` (the same set both ways), each with an equal value. The result's format, entries, skipped lines, unresolved lines (line, text, reason), and kit warnings (code, expected min and max, actual, message) equal the golden's `/pool`. Every expected value is read from the golden file at test time.
6. Classification, from a finished parse with 0 entries: no unresolved lines gives `EMPTY`; every unresolved line with reason `wrong-set` gives `WRONG_SET`; anything else gives `NOT_A_POOL`. A unit test per row of the background table, building each input in the test from the named fixture lines, asserts the kind. `trk-manabox-wrong-set-01.csv` itself (69 entries, 2 `wrong-set` lines) gives `Success`.
7. `PoolImporter.importStream(open, source)` reads the bytes as strict UTF-8 (malformed input is an error, not a replacement character) and gives `Failure(UNREADABLE)` for malformed bytes (for example `0xC3 0x28`) and for an `open` that throws `IOException`. Unit tests for both. A valid stream of `trk-manabox-01.csv` gives the same `Success` as criterion 5.
8. If the bundled set data cannot be loaded (a test seam with an empty asset source), `PoolImporter` reports a distinct `DataMissing` outcome. It is not an exception that reaches the caller. Unit test.
